## Plan (Gate 1)

### Scope
Complete `ReportPolicy` (add `export` ability) and create a shared `HasReportFilters` trait + `ReportFilterRequest` that all Phase 7 report services/controllers will use for consistent `session_id`, `sport_id`, `unit_id`, `tier_id` filtering.

### Boost MCP research (mandatory)

- `search-docs` packages=[laravel/framework] queries=["policy authorization before", "policy filters", "form request trait shared", "eloquent scope filtering"] → Confirmed `before()` method on policies for admin bypass; policy `export` method is a custom ability; traits on Form Requests are the established pattern.
- `database-schema` filter=participations,achievements → Confirmed FK chains: `achievements → participations → events → tournaments`. The 4 filter columns exist on: `participations.session_id`, `events.sport_id`, `tournaments.tier_id`, `teams.unit_id`.
- `grep` config/rbac.php → Only `reports.view` exists; no `reports.export`. Export will be gated by `reports.view` (same permission — exporting is a form of viewing).
- Skills consulted: `laravel-best-practices`.

### Schema / endpoints / pages

No migrations. No new endpoints. No new pages. Pure backend infrastructure.

**`ReportPolicy`** methods:
| Method | Gates on |
|---|---|
| `viewAny(User)` | `reports.view` *(existing)* |
| `view(User, mixed)` | `reports.view` *(existing)* |
| `export(User, mixed)` | `reports.view` *(new)* |

**`HasReportFilters` trait** (in `app/Concerns/`):
- `reportFilterRules(): array` — nullable integer + `exists:` rule for all 4 params
- `resolvedFilters(Request $request): array` — returns `['session_id' => ?int, 'sport_id' => ?int, 'unit_id' => ?int, 'tier_id' => ?int]`

**`ReportFilterRequest`** (in `app/Http/Requests/`):
- Uses `HasReportFilters`; `authorize()` checks `reports.view`; `rules()` delegates to `reportFilterRules()`

### Risk + mitigation
- **Risk:** Existing `ReportsMedalsController` and `MedalsPivotController` already do manual `$request->integer(...)` extraction — they should eventually be refactored to use the new trait, but that's not in scope here.
  **Mitigation:** Trait is additive; no existing code touched except adding one method to `ReportPolicy`.

### Test plan
- Pest Feature `ReportPolicyTest`: admin bypasses all; `reports.view` user passes `viewAny`, `view`, `export`; user without permission is denied all three.
- Pest Unit `HasReportFiltersTest`: `resolvedFilters()` returns nulls when params absent; returns correct ints when present; `reportFilterRules()` covers all 4 keys.

## Summary (Gate 3)

### What changed
- `app/Policies/ReportPolicy.php` — added `declare(strict_types=1)`; added `export(User $user, mixed $report): bool` → gates on `reports.view`
- `app/Concerns/HasReportFilters.php` — **new** trait; `reportFilterRules()` returns nullable/integer/exists rules for 4 params; `resolvedFilters(Request)` returns typed `?int` array
- `app/Http/Requests/ReportFilterRequest.php` — **new** Form Request using `HasReportFilters`; `authorize()` checks `reports.view`; `rules()` delegates to `reportFilterRules()`
- `tests/Feature/PolicyStubsTest.php` — added `ReportPolicy::export` dataset entry
- `tests/Unit/HasReportFiltersTest.php` — **new** unit test (4 scenarios)
- `docs/TASKS.md` — ticked P7-T01

### Decisions
- **`export` gates on `reports.view`** (not a new permission): exporting is a form of viewing; no separate `reports.export` permission needed until a use-case requires it.
- **Trait in `app/Concerns/`** — consistent with `PasswordValidationRules` and `ProfileValidationRules` already living there.
- **`0 → null` coercion in `resolvedFilters`**: using `?: null` so an empty `?session_id=0` param is treated as "no filter".

### Tests added
- `tests/Unit/HasReportFiltersTest.php` — 4 scenarios: rule keys, all-null, all-int, zero→null
- `tests/Feature/PolicyStubsTest.php` — +2 test runs (export with/without permission)

### Deferred / follow-ups
- `ReportsMedalsController` and `MedalsPivotController` still do manual filter extraction — will be refactored in P7-T02/T03 when those services are introduced.
