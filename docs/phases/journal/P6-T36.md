## Revision 2 — 2026-09-04

**Requested by user:** "clicking on print showing me blank output white page — check this first"
**Root cause:** The cloned print window copies every head node, including (a) the page's `data-print-preview-override` style whose `@media print` rules re-show `#quick-view-print-target` only under a `#app` ancestor that doesn't exist in the clone, and (b) `resources/css/app.css` print rules whose `body:has(#quick-view-print-target) > * { display: none }` (specificity 1-0-2) beats the stylesheet's own `#quick-view-print-target { display: block }` (1-0-0). Net effect in print media: everything hidden → blank white page. The member page had the identical bug (same copied logic).
**What changed:** Both `coaches/print-preview.tsx` and `members/print-preview.tsx` `handlePrint`:
1. Exclude `style[data-print-preview-override]` from the copied head nodes.
2. Inject corrective print CSS into the clone: `html body #quick-view-print-target { display: block !important; ... }` (specificity 1-0-3, beats the hide rule; placed after copied stylesheets so source order also wins).
3. Print trigger hardened: `readyState === 'complete'` → print immediately, otherwise one-shot `load` listener (previous `onload` assignment after `document.close()` could miss the event).
**Tests updated:** not applicable (frontend-only; prettier/eslint/types:check clean).
**Verification:** user to confirm print output renders in browser.

## Revision 3 — 2026-09-04

**Requested by user:** "I tried print — no CSS is working, only showing black and white text"
**Root cause:** `resources/css/app.css` print rules force monochrome inside `#quick-view-print-target` (`color: black !important; background: transparent !important; ...`) — designed for the quick-view component's plain print. Both redesigned print-preview sheets carry that id, so the clone inherited the black-and-white treatment. (Layout CSS was loading fine; only color/borders were stripped.)
**What changed:** Both `handlePrint` implementations:
1. Strip `id="quick-view-print-target"` from the cloned markup — the monochrome/hide rules no longer match the clone (the original page keeps the id for direct Ctrl+P).
2. Dropped the Revision-2 corrective `@media print` block (unnecessary once the id is gone).
3. Broadened `print-color-adjust: exact` from `img` to `*` so backgrounds/colors actually print.
**Tests updated:** not applicable (frontend-only; prettier/eslint/types:check clean).
**Verification:** user to confirm colored output in browser print.

## Revision 4 — 2026-09-04

**Requested by user:** "still not working, same issue showing on member print page now"
**Root cause:** The cloned-print-window approach cannot load the app's stylesheets in an `about:blank` window — the "black and white text" was unstyled markup all along (the CSS-specificity theory from Revision 2/3 was secondary).
**What changed:** Abandoned the clone approach entirely.
- `handlePrint` on both print-preview pages now reparents the live sheet `<div>` to `<body>`, calls `window.print()`, and restores the element on `afterprint` (fires even when the dialog is cancelled). Printing the live document means all CSS is present by construction.
- `resources/css/app.css` print block rewritten to match: hide top-level body siblings of the sheet (only possible now that the sheet is reparented to body), no monochrome forcing, `print-color-adjust: exact` kept so colors print.
- Deleted the per-page `data-print-preview-override` useEffect blocks (single source of truth in app.css now).
**Tests updated:** not applicable (frontend-only; eslint/types:check/build clean).
**Verification:** user to confirm print output renders styled + colored on coach and member.
