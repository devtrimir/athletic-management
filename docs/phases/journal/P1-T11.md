## Summary (Gate 3)

### What changed
- `app/Concerns/HasRoles.php` — trait with:
  - `roles(int $orgId)` → `Rbac::userRoles($this, $orgId)` (returns Collection of Role models)
  - `permissions(int $orgId)` → `Rbac::userPermissions($this, $orgId)`
  - `hasRole(string $code, int $orgId)` → boolean
  - `hasAnyRole(array $codes, int $orgId)` → boolean
  - `assignRole(Role|int $role, Organization|int $org, ?User $assignedBy)` → `UserRole::firstOrCreate([...])`
  - `revokeRole(Role|int $role, Organization|int $org)` → `UserRole::where([...])->delete()` + `Rbac::invalidate()`
- `app/Models/User.php` — `use HasRoles` added
- `tests/Feature/HasRolesTraitTest.php` — 9 tests covering all trait methods

### Decisions
- **`firstOrCreate` for `assignRole`:** Idempotent — calling twice doesn't create a duplicate. Uses composite PK uniqueness as the DB-level safety net.
- **Query-level delete in `revokeRole`:** `UserRole` has no auto-increment `id` — `Eloquent::delete()` on a retrieved instance builds `WHERE id = null` which silently deletes nothing. Query-level delete is the only reliable approach. `Rbac::invalidate()` called explicitly since the model's `booted()` `deleted` observer cannot fire without a proper delete event.
- **Accepts `Role|int` and `Organization|int`:** Callers may have either the model or just the ID; the trait normalises to int internally.
