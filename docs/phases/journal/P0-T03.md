### Risk + mitigation

- **Risk:** Larastan level 6 may flag errors in the existing Inertia/Fortify starter-kit code we didn't write.
  **Mitigation:** Run `vendor/bin/phpstan analyse` after install; if errors exist, run `vendor/bin/phpstan --generate-baseline` to snapshot them into `phpstan-baseline.neon`. Future code must resolve errors; baseline errors are explicitly tracked.

- **Risk:** `HorizonServiceProvider::gate()` default uses a hard-coded email list which can never be right in production.
  **Mitigation:** Replace with a deny-all gate (`return false;`) plus a `TODO P1-T03` comment to wire real RBAC once the Permission model exists. In `local` env Horizon is always accessible regardless of gate.

- **Risk:** Redis not running via Herd when tests execute.
  **Mitigation:** Feature test for the `/horizon` route uses the `sync` queue driver override so it never actually touches Redis; the test only asserts HTTP access control.

### Decisions

- **Deny-all Horizon gate:** The default hard-coded email approach is worse than deny-all. A `TODO P1-T03` comment marks exactly where real RBAC wires in. In `local` env Horizon is always accessible regardless of gate (Horizon behaviour).
- **Baseline instead of fixing starter-kit errors:** The `Password` rule return-type mismatch and Pest `TestCall` false-positives are starter-kit code we don't own. Fixing them in P0-T03 would be out of scope and would conflate our work with theirs. The baseline keeps the diff clean; any errors we introduce in future tasks will be caught immediately.
- **No `public/vendor/horizon`:** Horizon 5 serves its dashboard assets internally — `horizon:install` does not publish to `public/vendor/`.

### Tests added

- `tests/Feature/HorizonDashboardTest.php` — asserts `GET /horizon` returns 403 for both guests and authenticated users in non-local env (which confirms the deny-all gate works)
